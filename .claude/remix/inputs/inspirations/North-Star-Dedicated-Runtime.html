01 / The Problem

Some workloads need a
dedicated runtime.

High-frequency updates, real-time pricing, autonomous agents — these workloads demand guaranteed throughput. A shared queue will never give it to them.

case_01

On-Chain Oracles

Every write costs gas and waits behind unrelated traffic. Reads return stale prices while fresh updates sit stuck in the queue.

stale_reads queue_lag
case_02

Autonomous Agents

Every decision loop is gated by block time. Agents can't react faster than the chain confirms — and that ceiling is too low.

block_bound latency
case_03

On-Chain Orderbooks

Thousands of updates per second, but shared throughput can only ever carry a fraction. The book never reflects the market in real time.

throughput_cap contention

…and any workload that demands guaranteed throughput.

The North Star Approach
02 / The Solution

How North Star
solves it.

Instead of fighting for shared block space, your app gets its own temporary runtime. Dedicated compute where state updates are near-free — then everything settles back to Solana.

01
step.open_session()

Your app opens a session

When you need dedicated speed, you call North Star. One SDK call — that's the entire integration surface.

02
runtime.allocated

You get a private runtime

Dedicated compute, zero contention, over 1M TPS. State updates become near-free for the duration of your session.

1M+ TPS no_contention ~0 fee
03
settle.to_solana()

Results settle back to Solana

When the session closes, all state settles on-chain — fully verifiable. The runtime disappears, leaving only the proof.

tl;dr — Think of it as renting a private server, except it's on-chain, fully verifiable, and disappears the moment you're done.
